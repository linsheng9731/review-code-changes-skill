# Code Review 助手

辅助开发者理解变更并集中审查风险。默认中文，代码标识符保留原文。保持被审查代码不变；把 review 注释写在报告中。修复、发布 PR 评论、合并和部署须属于用户另外授权的任务。

## 1. 锁定范围与逐处清单

- 阅读适用的 AGENTS.md、需求、PR 描述和项目规范。区分明确需求与推断意图；缺少需求时仍先审查代码，把必要性的不确定处标为待确认。
- 遵循指定仓库、PR、base/head、提交或文件范围。PR 使用其实际 base/head 与 merge-base，不假设主分支名称。单提交使用父提交到该提交的直接 diff；合并提交说明选择的父提交。只在范围无法确定时提问。
- 未指定范围且已有本地仓库时，默认审查相对 HEAD 的已跟踪本地改动及未跟踪源文件，并声明默认值。无改动则说明；无仓库或 diff 则请求材料。
- 固定 base/head SHA、工作区状态、采集时间、diff 摘要。使用 scripts/collect_changes.py 建立文件和 hunk 清单；脚本不可用时用 Git/PR 工具等价建立清单。逐一读取真实 diff 和上下文，不能只读采集统计。
- 以 `--unified=0` 的连续实际改动块建立稳定 C ID 清单。用于阅读的带上下文 diff 可能把相邻块合成一个显示区域，不能据此重建 ID、改变覆盖总数或强行合并改动点；不同目的的原始块仍分别归组。采集脚本只读 Git，不属于运行待审项目。
- 分支采集：`python3 <skill>/scripts/collect_changes.py --repo <repo> --scope branch --base <base> --head <head> --out <scratch>/changes.json`。本地使用 `--scope all`；另支持 staged、worktree。脚本输出到待审仓库外。
- 对未跟踪文件读取完整内容并按逻辑单元补充 U001 等 ID；采集器仅列路径。对无文本块的二进制、生成文件、锁文件、纯重命名等补充 F001 等文件级 ID 和审查限制。重命名采集为删除/新增，需核对实际旧/新路径。
- 保留旧、新路径及两侧行号；删除使用旧版本定位，新增/修改使用新版本定位。本地代码用绝对 sandbox 文件链接并另列行号；远程仅使用已验证 URL 和固定提交 SHA，不虚构链接。

## 2. 追踪真实影响并分组

- 从改动入口追踪调用者、被调用者、共享函数消费者、状态读写、数据结构、事件/队列、配置与测试。读取关键实现，不能凭文件名或提交标题总结。
- 每项记录「旧行为 → 新行为 → 用户/系统影响」，标注新增、修改、删除、移动或无行为变化。
- 按业务流程分组核心改动：直接实现目标行为、修改关键契约或高风险共享路径。非核心包括格式、文档、机械重命名等支持性改动；测试需解释验证行为。分类与风险独立，小配置/依赖改动仍可能高风险。
- 以具体“改动点”而不是文件/hunk 为核心区的阅读单位，分配 G001 等 ID。每个改动点回答一个明确的行为变化，例如“空文本在扣费前拒绝”。为实现该行为而改动的入口、参数传递、共享实现、配置及相关测试可以跨文件聚合；同一文件中意图不同的 hunk 分到不同改动点。不要以笼统的“后端调整”“生成优化”把无关改动堆在一起。
- 先建立 `改动点 G ID → 所含 C/U/F ID → 文件及行号 → 独立说明` 的映射。每个改动块有一个主归属；共享块在主归属处展示，其他改动点链接引用，不重复展示或重复计算。hunk 内有不同意图时标子项并明确共享关系，不能裁掉另一意图的代码。
- 对无需求依据、意外共享契约变化或无关业务改动，列入“非预期/范围待确认”；依据证据说明，不直接指控越界。

## 3. 列出重点审查代码

读取 [references/review-rules.md](references/review-rules.md)，检查具体触发条件下的功能、权限、数据一致性、错误恢复、资源释放、兼容与性能问题。

- 区分已确认问题和高度可疑、待验证项，分别计数。证据不足时明确缺什么，不凑数。
- 每项包含稳定 R001 ID、P0–P3、置信度、最小定位、关联 C/U/F ID、触发条件、实际证据、后果、修复方向和验证方法。确认问题需解释完整失败链。
- 每项先提供**通俗解释**，再给技术依据。标题直接说人能观察到的结果，不用函数名或术语堆叠。白话部分必含：一句话说明问题、什么操作/条件会触发、一个具体例子、用户或系统会遇到什么、为什么发生、怎么改/怎么验证。让不了解这段实现的开发者先读这一部分就能理解。
- 用「用户做了什么 → 程序现在怎么处理 → 出现什么错误结果」解释。明确正常情况下本来应该怎样。例子必须符合代码证据；未实际执行则标“举例说明”，不要把假设当复现、虚构 UI 文案、金额、频率或生产事故。待验证问题在白话里也保留“在……条件下可能……”及待确认条件。
- 把“幂等、竞态、契约、原子性、补偿、背压”等词解释成当前场景中的动作和结果；需要保留术语时首次附白话解释。用短句，把一个失败链拆成步骤，不把文件名、符号、SHA 和证据全部塞入首段。
- 按影响定级：P0 为无特定前提的灾难性阻断；P1 为重要路径故障或重大安全/数据风险；P2 为有限场景实质缺陷；P3 为低影响改进。风格偏好不升级为缺陷。
- 同根因跨文件用一张卡片关联多处，避免重复计数。既有问题用 base 证据单列；本次扩大影响时明确新增影响。
- 按风险执行相关已有测试或最小复现；先检查命令，避免改写项目或调用付费/生产服务的测试。记录命令、实际结果、未运行原因；静态阅读不能写成测试通过。

## 4. 绘制受影响的核心流程

- 画真实业务/数据/控制流程，不能以文件清单替代。展示相关入口、决策、共享组件、外部依赖、成功/失败/取消路径及持久化边界。
- 图边基于实际调用、事件或数据流；推断关系使用虚线并注明待确认。图旁描述关键「旧 → 新」行为差异。
- 节点标记 `[新增 C001]`、`[修改 C002]`、`[删除 C003]`、`[未改动但受影响]`，风险关联 R001。图下定位表把节点对应到真实符号、文件与行号。
- Markdown 使用 Mermaid；HTML 使用可离线查看的内联 SVG，依据同一节点/边清单生成，不依赖 CDN。不要把 Mermaid 原文当成已渲染图。
- 使用从上到下布局、短标签、图例和关键分支；复杂流程拆图，每行至多五个节点。简单流程仍画准确的小图；机械改动画现有受影响流程并注明无行为变化，业务流程不可判断则画依赖图并说明限制。

## 5. 为每处改动写 review 注释

- 每个连续 diff hunk 都有 C001 等稳定 ID。一个 hunk 含不同意图时拆子项，并注明各子项的具体行号。同意图跨 hunk 可复用整体说明，但每个有独立位置的代码块仍在原地显示其作用和必要性，不能只留远处的说明链接。
- 核心、非核心、删除、测试、迁移、配置、新增文件全部注释。重复机械改动可合并表格，仍逐项列定位，不用“其余类似”跳过。
- 每条注释必含：**位置及变更前后**；**意图**（需求依据或推断）；**作用**（实际行为和上下游影响）；**必要性**（必须/可选/疑似多余/待确认 + 理由）；**审查结论/风险**（关联 R ID 或未发现明确问题）；**验证建议/已验证证据**。
- 意图、作用、必要性和风险先用常用词说明。例如用“去掉这段后，失败任务已经扣掉的额度不会退回”，而不是只写“补偿语义缺失”。流程图优先使用业务动作作标签，函数名放定位表。Summary 用白话说优先修什么、影响谁。
- 判断必要性时说明移除后哪个目标、契约或验证失败。不能因“增加校验”自动判必须，不能因“重构”自动判多余。材料不足判待确认。
- 用代表性 before/after 或 diff 摘录辅助理解，但不替代剩余改动块注释。遮蔽凭证/私人数据并注明，不原样复制到报告。
- HTML 中的 diff 默认使用参考图的左右对比：左侧旧代码的删除行用浅红背景与 `−`，右侧新代码的新增行用浅绿背景与 `+`，保留两侧独立的真实行号。上下文行保持白底，对侧没有代码时用空白占位；修改块按同一表格行对齐，长代码自动换行并保留缩进。不要用上下两个代码块或仅着色的 unified diff 替代左右对比。
- 使用 `scripts/render_diff.py --input <单文件单hunk.diff> --out <fragment.html> --hunk-ids C001 --old-label <旧版本说明> --new-label <新版本说明>` 生成已转义的双栏 HTML 片段，填入 [assets/review-unit.html](assets/review-unit.html)。每个 review unit 在同一边框内绑定**准确代码 diff + 紧随其后的逐处说明**；再把这些完整单元聚合到同一改动点。说明不能拆到组末尾的独立章节，也不能只有编号跳转。Markdown 同样在每段 diff 后紧跟该段说明。
- 一段 hunk 含多处不同意图时，说明子项明确标出对应旧/新行号；必要时在相关行组后使用横跨左右栏的批注行。保留代码原貌，将批注标为“Review 注释”，不能让读者误以为它是源码。默认作用与必要性简短且展开，详细证据可以在这个单元内折叠。

## 6. 生成参考面板形式的报告

读取 [references/report-contract.md](references/report-contract.md)，沿用 [assets/report.html](assets/report.html) 的白底、问题卡片、业务分组、影响图、可折叠文件列表和注释块。默认交付离线 HTML 与含相同内容的 Markdown；用户指定 inline/Markdown 时遵从，不强制文件。

核心区复用 [assets/change-group.html](assets/change-group.html)，每组固定顺序：**改动点标题 → 1–2 句整体目的及旧/新行为 → 多个“diff + 对应说明”完整单元 → 整体风险/验证结论**。聚合的对象是完整评审单元；代码与说明在视觉上和 DOM 中都属于同一容器。可按文件显示小标题，但不要重新排成文件清单或重复整体目的。相关测试附在该组并标“配套测试/非核心”，非核心区仅交叉引用，保持唯一覆盖。

HTML 报告使用左侧固定导航目录，包含全部章节，并在“核心改动点”下列出实际 G ID 与通俗标题，点击直达该组。导航与正文使用同一组数据生成，不能链接到不存在的组。目录独立滚动，正文留出左侧空间；窄屏改为正文上方的原生可折叠目录，打印时隐藏。目录不逐项堆列每个 hunk，具体 diff 与说明仍在组内就地绑定。

依次输出：
1. 标题与范围、整体 Summary、核心/非核心摘要、优先阅读建议。
2. CR 问题汇总：已确认/待验证数量、P0–P3；每张可疑代码卡片先放完整通俗解释和例子，随后放可展开的技术依据。
3. 核心改动点：以 G001 等具体改动点分组，聚合跨文件完整评审单元；每个 diff 的作用、必要性和风险直接绑定在该段代码旁或下方。
4. 影响链路：核心流程图、图例、定位表、旧/新行为。
5. 非预期改动与范围待确认项。
6. 非核心改动：按文件折叠，仍包含全部 review 注释。
7. 验证结果、未决问题与覆盖清单。

用锚点连接问题、图节点和注释。计数来自实际数据。高风险项默认展开；折叠使用原生 details/summary。不要添加未经授权的一键修复/发布按钮。转义代码和仓库文本，使用静态 HTML/CSS，不能让不可信文本变成脚本/HTML。

遵循当前环境的文件保存规则：ChatGPT Work 独立报告保存为用户可访问文件；CLI 使用指定位置或仓库外目录。不要写报告到待审仓库而污染 diff。最终回复链接报告、指出重点，不代替开发者批准。

## 7. 交付准出条件

- 清单中每个 hunk、未跟踪文件、无文本改动均有 ID、注释或明确限制。展示 `已分析数 / 总数`、遗漏 ID 和原因；未审完写“部分审查”，不声称全量完成。
- 验证核心区按改动点组织，且每个实际 diff 与对应说明位于同一个 `.review-unit` 内。仅靠跳转关联不合格；必须在读完这段代码的同一处直接看见作用与必要性，再进入下一段。核查行号、锚点、覆盖与唯一归属，不能遗漏或混入无关改动。Summary、风险卡片、流程图和覆盖表均能关联 G/C ID。
- 核实定位、计数、必要性理由、风险证据与图边，确保 HTML/Markdown 内容一致、无占位符。
- 逐项检查通俗解释：不看代码，能否回答“什么时候发生、正常应该怎样、实际怎样、影响谁、为什么、怎么修/验证”？能否看到具体例子？术语是否解释？白话与技术证据的条件、严重性和确定程度是否一致？只把术语换成另一个术语不算完成。
- 复核范围是否变化：head/工作区 diff 改变则重新采集并审查变化部分；未跟踪文件内容另做指纹比对，不让过期报告冒充当前结果。
- 验证折叠、锚点、SVG 标签和代码宽度。有渲染工具时实际渲染检查，否则注明未做视觉验证。
- 核对左侧目录覆盖全部章节与实际核心改动点，所有跳转目标唯一且存在；长标题能换行，长目录独立滚动，窄屏可折叠且不遮挡正文，打印无导航留白。
- 检查双栏 diff 的旧/新行号、删除/新增方向、占位行和换行后行高；纯新增/纯删除也保留空的另一侧，窄屏在组件内横向滚动，不让整份报告溢出。
- 区分“未发现明确缺陷”与“安全/可合并”，列证据及测试限制。不改代码、不发送评论。
