## 元信息与 Summary

记录仓库、目标、base/head SHA 或本地范围、采集时间、文件数及增删行数、覆盖比例、需求来源。不能精确统计时注明。用 2–5 句讲目标与新行为，再并列核心/非核心摘要，指出优先读的 R/C ID。

## 问题卡片

> **R001 · P1 · 高度可疑 · 中置信度：用白话说明错误结果的标题**
>
> **一句话说明：** 先说发生什么，不要求读者先懂函数名或术语。
>
> **什么时候会发生：** 用户操作或后台触发条件，明确必要前提。
>
> **举个例子：** 用户做什么 → 代码怎么处理 → 实际结果；对比应该出现的正常结果。注明“实际复现”或“举例说明”。
>
> **有什么影响：** 谁会受影响、看到什么或丢失什么；仅后台问题也用具体系统行为解释，不强行编用户界面。
>
> **为什么会这样：** 用 1–3 个短步骤说明因果，术语首次解释。
>
> **怎么改 / 怎么确认修好了：** 用直接动作说明修复方向和可观察的验证结果。
>
> **技术依据（HTML 可折叠）：** 精确位置与版本、关联 C ID、关键代码、失败链、执行结果、证据边界和待确认材料。

白话内容与例子默认完整展示，技术依据用 `<details class="technical"><summary>查看代码依据与验证细节</summary>…</details>` 放后面。高风险卡片本身保持展开，不能把通俗解释一并藏起来。Markdown 先放相同白话，再列技术依据。问题链接跳到该处注释；严重性与证据状态分别展示，按独立根因计数。

HTML 用 `.plain-summary` 突出一句话说明，用 `.plain-example` 展示场景例子，复用模板样式。两个区域里的仓库文本仍须转义。

### 表述样例（教学示例，不能当成实际 PR 结论）

避免只写：“异常路径删除补偿，导致计费契约回归。”

改写成：

> **生成失败了，已经扣掉的额度却没有退回。**
>
> **什么时候会发生：** 用户开始生成后，语音服务超时或报错。
>
> **举例说明：** 用户原本有 2 次额度。开始生成时扣掉 1 次，随后服务失败，没有产出音频。原来的代码会把那次额度退回，新代码直接返回失败，余额只剩 1 次。保留原有失败退款规则时，余额应该仍是 2 次。
>
> **为什么：** 新的错误处理返回了“失败”，但删掉了原来返还额度的那一步。
>
> **怎么改：** 在返回失败前退回额度，同时保留新的失败结果格式。
>
> **怎么验证：** 让测试中的语音服务故意报错，检查结果是失败、余额仍为 2 次。再检查正常生成时仍只扣 1 次。

实际卡片仍需补齐自己的影响说明、位置、证据和不确定性。数字仅作例子；不能暗示来自生产数据。

## 核心区：按改动点聚合，说明直接绑定代码

把核心区划分为 G001 等具体改动点，每组只讲一个目标/行为变化。一个改动点可以包含多个文件，一个文件可以服务多个改动点。聚合的是完整“diff + Review 注释”单元，不能把全部代码与全部说明分成两块。

每组固定结构：

1. **标题与整体说明**：1–2 句说明为什么改、旧行为变成什么新行为；列文件数、块数及关联风险，整体目的讲一次。
2. **完整评审单元列表**：每个 `.review-unit` 包含自己的路径/C ID/旧新行号、红绿双栏 diff，以及紧贴这段 diff 的 `.review-note`。显示顺序是“C001 代码 → C001 说明 → C002 代码 → C002 说明”。代码和注释共享边框与背景分区，读者无需滚到组末尾或点击链接才知道这段作用。
3. **整体结论**：1–2 句说明这些单元如何配合、优先验证或修复什么；引用 R ID，不重复问题全文。

复用 assets/review-unit.html：填充 UNIT_ID、UNIT_TITLE、UNIT_META、UNIT_DIFF、UNIT_NOTE。再把各完整单元填入 assets/change-group.html 的 GROUP_REVIEW_UNITS，连同 GROUP_ID、GROUP_TITLE、GROUP_META、GROUP_INTRO、GROUP_CONCLUSION 填完，插入主模板 CORE_CHANGES。Markdown 同样每段 diff 后立即跟随它的说明。

### 代码与注释的准确绑定

- 默认一个实际 hunk 对应一个评审单元。仅选属于本组的真实 hunk，保留代码、hunk 头和行号；不要把别的改动点整份文件代码塞进来。
- 对单 hunk 运行 `scripts/render_diff.py --hunk-ids C001 ...`，生成 `diff-C001` 锚点及 `#note-C001` 链接。评审单元用 `id="C001"`，注释用 `id="note-C001"`，注释返回 `#diff-C001`。这三者必须位于同一 `.review-unit` 内。
- 每处说明必含意图、作用、必要性及理由、风险/验证与位置；作用和必要性简短、白话、默认展开，详细代码依据可在该单元内部折叠。
- hunk 内多个不同意图分说明子项，并分别标明对应行号。必要时在对应行组后插入横跨六列的 Review 批注行；必须明显区别于源码，不凭相邻位置猜测所指行。
- 不使用独立的组末尾“逐处说明”章节，也不把多个单元的注释集中到页面另一侧。锚点用于便捷定位，不能替代视觉绑定。

### 聚合边界与完整性

- ID、归组和覆盖数以采集器的零上下文改动块为基准。普通 diff 添加上下文造成显示合并，不改变这些块的归属。
- 多个 hunk 默认分别渲染成完整单元；若合并一张表，必须在各 hunk 后插入它自己的批注，不能把所有注释堆到表末尾。跨文件不得伪装成同一连续代码。
- 每个 C/U/F ID 有一个主归属组；共享块只展示一次，其他组链接到完整单元。混合 hunk 的子项不增加覆盖计数。
- 相关测试可附在本改动点末尾，标“配套测试/非核心”，仍使用代码与说明绑定的完整单元。非核心章节仅交叉引用；其他非核心改动按文件折叠，但每处代码与说明仍在一起。
- 长组可整体折叠，高风险组默认展开。不要单独折叠作用与必要性，让读者展开代码后仍需到别处寻找说明。
- 覆盖表记录主归属 G ID、完整单元/代码/注释锚点及分类；Summary 链接 G 卡片，风险卡片链接准确单元。

### 阅读结构示意（教学示例）

```text
G001 下载接口采用新的地址字段
整体说明：服务端与页面同步使用新字段，保持下载可用。

完整单元 C001：接口返回对象的左右 diff
  紧贴代码的说明：返回什么、作用、是否必要、风险与验证。
完整单元 C002：页面读取地址的左右 diff
  紧贴代码的说明：如何读取新字段、作用、是否必要、风险与验证。
完整单元 C003：配套测试的左右 diff
  紧贴代码的说明：保护哪项行为、是否必要、风险与验证。

整体结论：这三处如何配合完成字段切换。
```

## 每处 review 注释

```text
C001 · 新增/修改/删除/移动 · 核心/非核心 · 必须/可选/疑似多余/待确认
位置：旧路径 old Lx–y；新路径 new Lx–y；覆盖 hunk ID
变更前 → 变更后：可核实的行为差异
意图：需求依据，或明确“根据代码推断”
作用：受影响的调用者、状态、数据或外部交互
必要性：结论 + 移除后果/保留收益/待确认依据
Review：关联 R001，或未发现明确问题；给证据边界
验证：实际结果，或开发者需要验证的案例
```

核心与非核心区都将注释直接绑定在对应 diff 的完整评审单元中。核心/高风险默认展开；非核心按文件折叠，但不能把该文件的代码和说明拆开。

每条注释的解释也先用白话，函数名保留在定位与证据部分。必要性说明用“如果删掉，会导致……”或“保留的好处是……”，不要只写“保持一致性”“保证正确性”。Summary 和图标签同样先写实际动作与影响。

## 双栏 diff（HTML 默认）

- 使用 scripts/render_diff.py 从单文件的 unified diff 生成片段，复用 assets/report.html 的 `.diff-view` / `.diff-table` 样式。核心区按实际 hunk 渲染并绑定注释，再聚合完整单元；非核心区同样就地绑定说明。删除敏感内容后再渲染，不把凭证放进报告。
- 左侧标“旧代码 / base”，右侧标“新代码 / head”，可附真实 SHA/路径。删除行浅红 `#ffebe9`，左行号栏较深红 `#ffd7d5`；新增行浅绿 `#dafbe1`，右行号栏较深绿 `#aceebb`。颜色之外保留 `−`/`+`，上下文白底，空侧灰底。
- 每个显示行含六列：旧行号、旧标记、旧代码、新行号、新标记、新代码。用一张 table 对齐两侧行高；不要用两张独立表格。代码保留空格/缩进，自动换行，不把换行后的视觉行误当真实新行号。
- 修改块将连续删除与新增按各自顺序并排呈现，长度不同用空侧补齐。这是阅读对齐，不代表两侧每行都存在语义的一对一对应；以真实 diff 为准。纯删除、纯新增、文件尾无换行以及多 hunk 均明确展示。
- 每个 hunk 头显示真实 `@@ -old,count +new,count @@`；hunk 间不补造未提供的上下文。旧侧行号只由旧版本推进，新侧只由新版本推进。
- 长代码自动换行，窄屏保持双栏并在组件内横向滚动。每段 diff 的 review 注释直接绑定在同一评审单元内，不能删减意图/作用/必要性字段。
- Markdown 输出保留等价 unified diff。HTML 要真正的红绿左右对比，不能仅写“before/after”文字或展示原始 patch。

## 图与覆盖

图节点定位表：节点 ID、业务动作、变更状态、旧/新行为、符号/位置、关联改动/风险 ID。HTML SVG 和 Markdown Mermaid 使用相同节点/边。

尾部包含测试命令与结果、未运行原因、未决问题，以及覆盖表（ID、文件行号、注释锚点、已分析/限制）。展示已分析 N / 总 M，未覆盖 ID 与原因。无文本文件和新增文件也列入。给优先验证/修复建议，不批准 PR。

## HTML 填充

复制 assets/report.html 到输出位置，替换全部 `{{...}}`：TITLE、META、COUNTS、TOC_CORE_GROUPS、SUMMARY、CORE_SUMMARY、SECONDARY_SUMMARY、FINDINGS、CORE_CHANGES、FLOW_SVG、FLOW_MAP、UNEXPECTED、SECONDARY_CHANGES、VALIDATION、COVERAGE。

左侧目录固定展示各章节，核心改动点下嵌套实际 G 组。`TOC_CORE_GROUPS` 由生成正文的同一组数据构造：每组一个 `<li><a href="#G001">G001 · 空文本在扣费前拒绝</a></li>`，标题转义，顺序与正文一致；没有核心组时填空字符串。导航定位到整个改动点，组内仍逐段绑定 diff 与说明。保留模板中 summary/findings/core/flow/unexpected/secondary/validation/coverage 的唯一章节锚点；不展示的章节必须同时移除对应菜单项，不能留失效链接。

桌面目录独立滚动，正文留出左侧空间，不覆盖红绿双栏 diff；长标题换行。宽度不超过 1100px 时目录移到正文上方，可通过原生 details/summary 折叠；不依赖 JavaScript。打印隐藏目录并移除正文左侧留白。交付前逐项核查菜单链接、G ID 与正文对应关系。

仓库文本只插入已转义的 text/code：转义 `& < > " '`。验证链接协议，仅用已知 http/https/sandbox 或内部锚点。仅由 agent 构造可信布局标签；不要把 PR/代码文本直接当 HTML 插入。保持无脚本、无外部网络依赖。

改动点/问题/完整单元用唯一 `id="G001"`/`id="R001"`/`id="C001"`，diff 用 `id="diff-C001"`，注释用 `id="note-C001"`。问题与单元、diff 与说明互链；不要在不同片段上复用锚点。SVG 用 viewBox、箭头、分支标签和图例；不要把 Mermaid 原文当成渲染图。
